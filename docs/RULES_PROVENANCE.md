# Rules and computer-opponent provenance

The PC client contains the battle arithmetic, growth rules, board effects and computer decisions. The server uses those routines for computer and human matches with two or three players, with saved results and optional card prizes, wagers, ratings and practice departures. Seeds, draw order, reward rules and recovery are this server's choices. [Coverage](EMULATION_COVERAGE.md) tracks the wider protocol; mapped fields and headless tests do not show that every client screen works.

The client also has **network-independent simulation code**, but that does not mean the released menus offer an offline mode. The evidence below comes from running isolated client routines, without launching the game.

All addresses are client virtual addresses, image base `10000000`. `P=102B63E0`, `G=DWORD[102B63C4]`. The full layouts and arithmetic are in [TetraPackets](https://github.com/TetraSlop/packets) (`client/rules.md`, `client/board.md`, `client/computer-player.md`).

The local calculator uses `final=floor(((r0&65535)%(base*multiplier+1)+(r1&65535)%(base*multiplier+1))/2)`. If both finals are 0, it draws two additional `rand()&1` values once. It does not reroll every tie inside that helper. Native CRT function 101E2E44 is ported as `state=(state*214013+2531011)&0xffffffff; rand=(state>>16)&32767`. Using this client-local RNG on the server remains a selected policy because historical online seeds and draw ordering are unknown.

## What the offline/computer branches actually prove

Constructor 100B9A00 reads global 102B624C and writes its nonzero predicate into both G.172 (receive gates) and P.EA (send/local-calculation gates), at 100B9A89..100B9A9C. For constructor mode0/alternate0:

- **Global0:** branch 100B9B46..100B9B56 chooses the local path; 100B9BA7 sets G.171=1, enabling simulated-player choices.100B9C94..100B9CA7 locally generates one card for every catalogue model. It enters major2, whose 100BCC28 branch skips ComGameInit initialization when G.172==0. Sends and normal gameplay receive waits are separately bypassed by the zero flags; the local battle and reward calculators become available.
- **Global nonzero:** 100B9D1B..100B9D2B chooses network computer setup; 100B9D88 sets G.171=0. Major2 calls 100BAD30, which waits for 43/02 ComGameInit. Local AI being present does not make this hosted computer route server-free.

The constructor-mode fixtures execute the original flag assignments, branch selection and major2 call gate for global0,1 and 12345678. The computer-init callee is replaced with a returning stub only to count whether it was called; initialization/rendering are not played.

There is a concrete all-zero constructor caller at 10191237..1019124F in event handler 10190DD0, reached by its event01FF1003 branch (10191098..101910A3). That is a code-level entry lead, **not proof the normal released menu exposes it or that startup assets/profile/save handling are complete without a service**. Another caller 1014A110 passes mode5 and must not be conflated with the mode0 local branch. Reaching the actual global0/mode0 path from the installed wrapper remains untested.

The hosted computer protocol is separate: 43/02 ComGameInit supplies local stats/rules and optionally ComList; 43/04 ComList supplies opponent entries; 43/06 ComGame submits rules and selected computer IDs (receivers 10102D21..10103039, sender 10106F3A..101072E2, UI sends 100EE95B/100EBBE9). The server supports this route with `computer_menu=True`, including all 30 original NPC records. Its alternate Continue Conf1/Ans1 sends only ComList04 and returns to configuration, matching sender 1010D375 and receiver 1010D5D9; the next wager debit waits for a committed ComGame choice. `tests/game/test_match_service.py` covers rematches, reconfiguration and that debit boundary; `tests/game/test_computer_menu_integration.py` exercises the encrypted three-round menu/rematch/reconfiguration flow. The default CPU route still uses seat 1 in an ordinary VsGameInit match, where Conf1 is rejected before changing votes. See TetraPackets `client/computer-player.md` for the client side.

## Remaining boundaries

- The original server's RNG scheduling, rewards, ratings and automatic event and Prize Center awards are unknown. Do not present this server's choices as original behavior.
- No participant reconnect/resume handshake is established. Recovery preserves committed results and recovers pending earned cards through the existing Returned Card collection path; it does not recreate an interrupted native scene. Economic/rated partial departures remain outside the supported continuation policy.
- Gameplay and prize requests carry no recovered round/choice identifier. Ordered delivery and current phase/seat checks remain necessary; a byte-identical old request that is also legal in a later round or prize choice cannot always be distinguished.
- The Computer menu now supports one human with one or two distinct original NPCs, including 25-cell games and 2↔3 reconfiguration. The client side is in TetraPackets `client/computer-player.md`. Native rendered checks of menus, special-board/prize/result scenes and observer pacing remain separate from the instruction and encrypted-service tests. The all-zero offline constructor path described above is still an unvalidated released-menu route.
